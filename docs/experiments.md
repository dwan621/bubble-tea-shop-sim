### Verdict

- Passed: **yes**
- Low load (λ = 1.00): 2/2 within ±5%
- High load (λ = 1.25): 4/4 within ±12%
- Archive ranking: E1, E2, E4, E3, E5, E6
- Python ranking: E1, E2, E4, E3, E6, E5
- The only ranking difference is the E5/E6 order: the archive has E6 (split + fast) a hair above E5 (fast only), the Python engine has E5 a hair above E6. Both gaps are around 1%, and at 88% utilisation the split break-even is already behind us, so a small penalty for splitting is the expected sign in this engine.

Deviation sources:

1. Different random streams: the AnyLogic model draws its own Poisson arrival stream and class uniforms, so a like-for-like single run differs by several percent even with the same parameters.
1. Single run versus 200 replicates: at 88% utilisation the queue is extremely sensitive to the random draw, so a single archived run is one sample from a wide distribution and the 200-replicate mean is the expected value (the visible high-load deviations are in the expected direction: this engine's mean is below the archived single run for E3-E6).
1. Stop-time accounting: AnyLogic counts only customers that reach the sink before the 1000-minute stop, while the Python engine drains the queue; the censored variant in this file isolates that effect (it moves the deviation by 2-4 percentage points, i.e. it explains part of, but not all, the raw difference).
1. Archival read-out windows: the archived revenue rate implies about 999.6 minutes while the archived utilisation display implies about 1027-1032 minutes, so the two archive columns are not on exactly the same denominator (see archive_utilization_audit).
1. E3 is internally inconsistent: the documented formula applied to E3's own revenueTotal and flowTimeTotal gives 337.4/hour, not the archived 349.478. Every other row reproduces to within 0.03%.
